# Proposed Fix: Split Thinking and Output in NDJSON Logs

## Problem Statement
Currently, when using `--logndjson`, the model's "thinking" process (from Ollama's `msg.thinking` field) is either combined into a single assistant message with `<thought>` tags or omitted entirely from the log. The user wants these to be split into two separate NDJSON lines: one for thinking and one for the actual output, including a marker to distinguish them.

Crucially, this splitting should **only** occur when the model's reasoning is provided via the API's dedicated `thinking` field. If the model simply includes `<think>` tags within its standard text content, it should remain as a single message to avoid breaking parsers that expect standard conversation formats.

## Proposed Solutions

### Solution 1: Explicit `mode` Field (Recommended)
Add a `mode` key to the `message` object in the NDJSON log. This is non-destructive and easy for downstream tools to parse.

**Example Log Output:**
```json
{"timestamp": "2026-08-18 18:28:38", "model": "lfm2.5-thinking:1.2b", "message": {"role": "assistant", "content": "Thinking process content...", "mode": "thinking"}}
{"timestamp": "2026-08-18 18:28:39", "model": "lfm2.5-thinking:1.2b", "message": {"role": "assistant", "content": "Actual response content...", "mode": "output"}}
```

**Pros:**
- Very clear and structured.
- Does not change the `role` field, maintaining compatibility with standard LLM conversation formats.
- Easy to filter logs by mode (e.g., `grep '"mode": "thinking"'`).

---

### Solution 2: Dedicated `role` for Thinking
Use a custom role name specifically for the thinking part of the message in the log.

**Example Log Output:**
```json
{"timestamp": "2026-08-18 18:28:38", "model": "lfm2.5-thinking:1.2b", "message": {"role": "thought", "content": "Thinking process content..."}}
{"timestamp": "2026-08-18 18:28:39", "model": "lfm2.5-thinking:1.2b", "message": {"role": "assistant", "content": "Actual response content..."}}
```

**Pros:**
- Extremely easy to identify using simple string matching on the `role` field.
- Follows a pattern similar to how some specialized APIs handle reasoning steps.

---

### Solution 3: Content Prefixing (Marker in Text)
If we want to keep the messages as standard assistant roles but distinguish them, we can prefix the content of the thinking message with a marker like `[THOUGHT]` and the output with `[OUTPUT]`.

**Example Log Output:**
```json
{"timestamp": "2026-08-18 18:28:38", "model": "lfm2.5-thinking:1.2b", "message": {"role": "assistant", "content": "[THOUGHT]\nThinking process content..."}}
{"timestamp": "2026-08-18 18:28:39", "model": "lfm2.5-thinking:1.2b", "message": {"role": "assistant", "content": "[OUTPUT]\nActual response content..."}}
```

**Pros:**
- No changes required to the JSON schema/structure.
- Human-readable even if viewed as raw text.

**Cons:**
- Harder for automated tools to parse reliably compared to Solution 1 or 2.
- Requires string manipulation on the content itself.

## Implementation Requirements (All Solutions)
1. **Detection Logic**: Only trigger splitting in `tool_base/engine.py` if `response_thinking` is non-empty AND it was populated via `msg.thinking`.
2. **Message History Integrity**: The `messages` list used for the conversation history should likely remain unchanged (one assistant message) to ensure subsequent turns are not confused by "thought" roles or modes, unless specifically requested otherwise. The split should primarily target the `ndjson_log_file_handle` output.
3. **No-Thinking Fallback**: If no thinking is present, continue logging a single standard assistant message as currently implemented.
