## 2. Unclear Issues and Detailed Explanations Requested in 001_QA.md

### F5: Q5.4 — CWD from Loaded Session (Detailed Explanation)

**Original question**: "Should the loaded session's `cwd` be used for subsequent session file paths, or should the current working directory be preserved?"

**Detailed explanation**:

The `serialize_session()` function stores the current working directory in the session file as the `cwd` key:
```python
if cwd:
    data["cwd"] = cwd
```

This `cwd` is used by `session_dir_for()` to determine where auto-saved session files are stored for a given project. The function `_encode_cwd(cwd)` creates a filesystem-safe slug from the cwd, and `session_dir_for(cwd, sessions_dir)` returns the session directory for that project.

When `--load` loads a session from another project (with a different `cwd` stored in the file), two behaviors are possible:

**Option A — Preserve loaded session's cwd**: After loading, all future autosave operations for this session would use the `cwd` from the loaded file. This means:
- The session would appear as if it belongs to the loaded file's project.
- `find_recent_session()` for the loaded project would find this session.
- `find_recent_session()` for the current project would NOT find this session.
- This could be confusing: the user is in project A but the session is stored under project B's directory.

**Option B — Use current working directory**: After loading, all future autosave operations use the current working directory. This means:
- The session is treated as belonging to the current project.
- The `cwd` in the loaded file is ignored after loading.
- The session would be found by `find_recent_session()` for the current project.

**Follow-up**: Which behavior is intended?

**Answer**
We should keep that simple. When we /save a session then cwd is not contained. 
When we /load or --load a sessionfile which is either an saved file then there is no cwd.
And when it is an autosave sessionfile then the that contained cwd has to be ignored. 
The current working directory is still used for all future autosave operations.

### F6: Q8.3 — "Valid but Not a Session File" (Detailed Explanation)

**Original question**: "What should happen if the JSON is valid but not a session file (missing required keys)?"

**Detailed explanation**:

The `serialize_session()` function always writes these keys:
- `model` (str) — always present
- `messages` (list) — always present
- `updated_at` (float) — always present

And optionally:
- `title`, `session_id`, `cwd`, `created_at`, `mode`, `skill`, `skill_text`, `system_prompt`, `loaded_tool_modules`, `ctx_compact`, `ctx_compact_threshold`, `ctx_compact_model`, `ctx_usage`, `ctx_usage_model`, `stats`

The `apply_session()` function reads these keys and ignores unknown ones. It relies on:
- `data.get("messages", [])` — defaults to empty list
- `data.get("model")` — used for model mismatch check

So a "valid JSON but not a session file" could mean:

**Case 1**: JSON is valid but has `model` and `messages` — is this a session file? Yes, it has the minimum required keys.

**Case 2**: JSON is valid but missing `model` — `apply_session()` would set `state.config.model` to `None` (from `data.get("model")`). This is silently accepted but might cause issues later.

**Case 3**: JSON is valid but missing `messages` — `apply_session()` would set `state.messages = []`. The session would be empty.

**Case 4**: JSON is valid but has none of the expected keys — `apply_session()` would still "succeed" with an empty session.

**Follow-up**:
- What is the **minimum** set of keys that makes a JSON file a valid lama_ole session file?
- Should `--load` require `model` and `messages` to be present, and error if either is missing?
- Should `--load` reject files that have none of the expected keys?
- Should `--load` accept files with only `messages` (but no `model`)?
- Should `--load` accept files with only `model` (but no `messages`)?

**Answer**

`--load` should accept files with only `messages` (but no `model`).

### F7: Q8.4 — "Validate File Was Created by lama_ole" (Detailed Explanation)

**Original question**: "Should `--load` validate that the file was created by lama_ole (check for expected keys)?"

**Detailed explanation**:

There are multiple levels of validation possible:

**Level 0 — No validation**: Trust that the user provides a valid file. Let `apply_session()` handle unknown formats gracefully (which it already does by ignoring unknown keys).

**Level 1 — Minimal validation**: Check that the file is valid JSON, is a regular file, and has at least one key that lama_ole recognizes (e.g., `messages` or `model`).

**Level 2 — Full validation**: Check that the file has all required lama_ole keys (`model`, `messages`) and that the structure matches expected types (e.g., `messages` is a list, `model` is a string).

**Level 3 — Strict validation**: Add a version field to session files and check it. Reject files from future lama_ole versions.

**Follow-up**:
- Which validation level is intended?
- Should `--load-info` use the same validation level, or a lower one (since it just needs to print partial info)?
- Should validation errors from `--load` be different from validation errors from `--stats`?

**Answer**
Level 1 is enough: Check that the file is valid JSON, is a regular file, and has at least one key that lama_ole recognizes: `messages`.

### F8: Q11.5 — Context Meter and Auto-Compaction from Loaded Session (Detailed Explanation)

**Original question**: "Should `--load` interact with `--ctx-meter` and auto-compaction settings from the loaded session?"

**Detailed explanation**:

The loaded session file may contain these context-related keys:
- `ctx_compact` (bool) — auto-compaction enabled/disabled
- `ctx_compact_threshold` (float) — auto-compaction threshold
- `ctx_compact_model` (str) — model used for compaction
- `ctx_usage` (dict) — context usage stats
- `ctx_usage_model` (str) — model for context usage

The `apply_session()` function already restores `ctx_compact`, `ctx_compact_threshold`, and `ctx_compact_model` from the loaded file.

The question is: should these **override** the CLI/env values set by the user?

For example:
- User runs: `lama_ole --chat --auto-compact --load saved.json`
- `saved.json` has `ctx_compact: false`
- Should auto-compaction be **enabled** (from CLI) or **disabled** (from session)?

**Follow-up**:
- Should CLI/env values take precedence over session values for `ctx_compact`, `ctx_compact_threshold`, and `ctx_compact_model`?
- Should `ctx_usage` and `ctx_usage_model` always be restored from the session (since they are historical stats, not settings)?
- Should `--ctx-meter` (the live context usage display) be affected by the loaded session's `ctx_compact` setting?

**Answer**
We change that completely. Only for model differences the user is getting asked. The parameters `ctx_*` should remain in the sessionfile for informal reasons only and never be applied to lama_ole runtime.
